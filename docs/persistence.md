# Local progress persistence

## Statistics snapshots

`statistics` is an optional validated map in the main state snapshot. The coordinator registers a `Session.setStatisticsProvider` callback; every ordinary checkpoint save copies finite, non-negative counters and accumulated active runtime into the same snapshot transaction as pose and cursor. `Session.statistics()` returns a defensive copy for resume. Older snapshots without statistics remain valid and load as an empty map. The validator bounds the map to 128 string-keyed numeric values; statistics remain observational and do not affect movement admission.

## Purpose

Keep the active single-turtle run's committed pose and traversed route durable, and stop safely when a restart cannot prove the turtle's physical pose.

## Implemented behavior

`src/persistence/startup.lua` decides whether the default `miner` command may create a run. Missing or completed state may start; active/incomplete state prints `miner status` and `miner resume` guidance and is never overwritten. Uncertain pose, corrupt state, and config mismatch remain explicit safe stops. A known-pose `NO_SUPPLY_CHEST` failure during a persisted service trip remains retryable by `miner resume`, which re-runs current chest validation from the committed service stage. Other fatal statuses remain refused. `tests/persistence_startup.lua` and `tests/persistence_recovery.lua` cover these decisions.

`src/persistence/state.lua` validates schema version 1 snapshots, allowed status/certainty/action enums, finite integer coordinates and config values, and the route graph's coordinate keys, adjacency, reversibility, home, and current-pose membership. It writes a temporary snapshot, validates the decoded snapshot against the full schema, rotates a valid active snapshot to `.bak`, and commits the temporary file. Loads prefer a valid active snapshot, then a valid backup, then promote a fully validated orphan `.tmp` only when both are unusable. Invalid temp content is never accepted, and an unpromoted temp is retained for diagnosis when the backup wins. Loads reject invalid expected configuration and mismatched saved configuration, and report `POSITION_UNCERTAIN` when a movement/turn intent remains pending. If no snapshot validates, `State.load` returns `STATE_CORRUPT`; it returns `STATE_MISSING` only when active, backup, and temporary files are all absent, the sole condition that permits starting a new run. The coordinator stops on corruption before prompting or initializing a run. `src/persistence/checkpoint.lua` owns run-state creation/loading and the durable checkpoint lifecycle: snapshotting the live pose/route/config, saving pending action intent, committing or cancelling an action, and recording fatal/complete status. Error-status snapshots require a string error code. When mining reports failure, the coordinator synchronously calls `markFatal` to save the error status and code before `main` returns. `Session.snapshotState` returns a defensive copy. `src/persistence/recovery.lua` classifies known, committed snapshots before the `resume` command can take action; pending, uncertain, corrupt, mismatched, vein-entry, in-slice stair, and unsupported active mining cursors fail closed. Every admitted boundary requires the resume descriptor's complete validated cursor to match the active cursor, including phase, route position, and `nextAction`; matching only a work-unit ID is insufficient. Service stages are admitted only when their saved cursor can itself be dispatched, their stage destination and original target are valid, and recorded routes connect the committed pose to base and back to the target. Before movement, `resume` validates route targets and budgets service/replay legs plus return reserve. It repeats interrupted unload/resupply from the committed pose and clears service only after exact target restoration. A committed `floor_complete` checkpoint with a matching saved landing can be replayed: resume returns to origin on recorded edges, replays recorded stair centreline moves, follows only saved clear edges to restore checkpoint pose/facing, and continues subsequent floors. The `status` command reads and reports a validated snapshot without creating a directory or issuing movement. `tests/persistence_recovery.lua`, `tests/active_baseline_wiring.lua`, and `tests/recovery_status.lua` verify these software boundaries; physical reboot timing and filesystem durability remain operator checks.

The active move/turn/dig adapters persist a typed `pendingAction` before invoking the turtle API through `src/persistence/physical_action.lua`. On literal success they immediately save the action commit; movement commits install the returned pose and route edge first. On literal API failure they cancel intent and retain the prior pose. Exceptions after intent, or failed post-action saves, leave the durable pending record to force `POSITION_UNCERTAIN` on reboot. Dig intent covers each bounded `DigClear` turtle dig attempt; it does not make the multi-action stair sweep resumable. Active/unwinding veins are resumed only by persisting an unwind stage, replaying recorded inverse breadcrumbs with a save after each edge, and clearing the excursion at the exact checkpoint before dispatching the saved mining cursor. Recovery validates route evidence and visited coordinates for every inverse landing. An `entering` vein remains refused because seed dig and entry movement can be ambiguous after reboot. A next-floor `cross_landing` cursor is resumed from the prior recorded landing, after validating its complete saved route geometry and budgeting the recorded route plus return commitment. The coordinator then crosses once, invokes the regular stair descent, and continues the remaining floors; after that resumed execution returns to surface origin, it now commits `status="complete"` just like the other resumable cursor paths. It never replays the crossing from the destination pose. This recovery check requires origin, mouth, rear, and landing landmarks with integer step counts, one- or four-block entry, and a home route. In-slice and landing-carve cursors remain rejected with distinct `STAIR_SLICE_RESUME_UNSUPPORTED` and `LANDING_CARVE_RESUME_UNSUPPORTED` reasons because the logical stair unit still lacks an exact persisted sub-action and inverse stack.

`src/mining/cursor.lua` defines validated logical cursors for the active baseline and route preparation. The coordinator persists each bounded unit before starting it. Snapshot validation requires every cursor field (`workDomain`, identity, floor/stair positions, branch pair/side, phase, offsets, and next action) to match across the active, resume, and service descriptors; a same-ID cursor with altered geometry is corrupt. Recovery also requires the committed pose to match the exact supported executor boundary. Main-shaft, junction, lower-outbound, turnaround, upper-return, and junction-descent cursors resume at their exact landing-derived phase and side. Branch return geometry uses the committed lower canonical junction pose after descent. The phase machine retains a legacy `branch_lower_return` transition for compatibility, but the active executor returns on the upper lane and descends at the junction; it never emits that cursor, which remains fail-closed. The `status` command reports the classifier result without movement.

Each active cursor also carries a work-unit origin pose, fixed outbound heading, configured route bounds, and `completionStatus`. `MiningCursor.withWorkUnit(progress, origin, config)` creates this descriptor at the committed checkpoint; branch return phases retain the outbound heading rather than the turtle's reverse-facing heading. `Session.setProgress` stores the framed cursor and resume checkpoint together. Final completion marks the terminal unit complete. Older schema-1 snapshots without these optional descriptor fields remain readable; newly written units include them. `tests/persistence_state.lua` checks roundtrip, route-frame handling, and rejection of tampered bounds.

Recovery validates persisted local `routeStack` data with `ActionStack.validate`. A non-empty stack at an in-slice stair cursor is refused as `STAIR_ACTION_PENDING_UNSUPPORTED`: inverse records do not prove which sweep action completed, so they cannot establish a safe physical pose or restart point. A malformed stack is refused as `ROUTE_STACK_INVALID`. Empty or absent stacks retain the existing cursor-specific recovery behavior.

`tests/persistence_recovery.lua` injects restart snapshots after durable move, turn, and dig intents, including valid provisional route inverse records. All must classify as `POSITION_UNCERTAIN` (or `RESUME_STATE_UNSAFE` when loaded without the storage-layer uncertainty code); a route edge alone never promotes an uncommitted action to a known checkpoint. It also covers every persisted service stage against supported branch outbound, turnaround, upper-return, and junction-descent cursors, and rejects a cursor changed during service. Active/unwinding vein records require exact cursor, breadcrumb geometry, visited-coordinate, and route evidence; ambiguous entering snapshots remain refused. A pending vein edge intent reloads as `POSITION_UNCERTAIN`. The crash fixture reloads an intermediate vein unwind from serialized bytes and executes its remaining inverse to the exact checkpoint; a separate injected inverse failure verifies immediate stop and retains the serialized breadcrumb. Its synthetic underlying main-shaft cursor remains correctly rejected as `MAIN_SHAFT_RESUME_UNSUPPORTED`, so this does not claim coordinator-level restart admission. `tests/persistence_state.lua` covers initial and replacement orphan-temp promotion, backup preservation, corrupt temp, and schema-invalid temp. Physical reboot timing and filesystem power-loss behavior still require in-world verification.

The software crash/error matrix is verified by the 63-file Lua suite. Covered boundaries include failure to persist intent (no turtle call), explicit API failure (cancel without pose commit), exception after intent (`ACTION_RESULT_UNCERTAIN` and durable pending intent), failure to persist a successful action commit (stop with pending intent), movement/turn/dig pending snapshots (`POSITION_UNCERTAIN`), corrupt/mismatched snapshots, invalid route evidence, unsupported cursors, failed inverse movement, and interruption after a committed inverse. Run each `tests/**/*.lua` from the repository root with Lua 5.4; syntax-check all files under `src/` and `tests/`. The suite does not simulate real power loss or prove CC:Tweaked filesystem durability.

Each snapshot also contains `resumeCheckpoint = { pose, progress }`, the last durable committed pose and next logical cursor. The checkpoint is a recovery target descriptor, not permission to move after reboot. For `floor_complete`, resume returns to origin, replays recorded stairs and known clear routes to the saved landing, then continues remaining floors. Other admitted cursors resume only at their committed pose after recovery validation. `src/fuel/resume_commitment.lua` exposes `targetFuelForTrips(homeMoves, resumeMoves, reserve, workStepMoves)`. Unsupported lower-return, pending-action, service, and vein states remain fail-closed.

Optional `service = { stage, checkpoint, resumeProgress }` records persist a service trip independently of the mining cursor. Allowed stages are `returning`, `at_base`, `unloading`, and `resuming`; each write validates and retains the exact checkpoint pose and cursor. `Session.setService` is called before home travel and at each stage boundary; service clears the record only after verified route return to the saved pose. After restart, the service destination is validated against base or the original resume target, then the service executor safely repeats unloading and resupply from the committed pose. Pending physical actions remain uncertain and are never replayed.

Snapshots optionally contain `floorLandings`, keyed by floor number. Each record stores the segment origin, mouth, rear-centre, landing-centre, step count, and entry length. Validation checks the geometric displacement, contiguous floor-to-floor origins, and that route landmarks exist in the recorded known-route graph. `Session.recordFloorLanding` persists a validated record with the current pose/graph; `floorLanding(floor)` and `floorLandings()` return defensive copies. Older snapshots without this optional field remain valid.

Snapshots also carry an optional `routeStack` of dense `{action, inverse}` records. New sessions initialise it empty; old snapshots without it remain readable. The action-stack validator bounds depth and accepts only known inverse pairs. `Session.recordRouteAction` writes an explicit reversible action, and `Session.commitRouteInverse` removes only the matching top record after the caller has completed and committed that inverse. `Session.beginRouteAction` atomically writes a reversible action with its pending move/turn intent before the physical call. `Session.commitRouteAction` atomically writes the committed pose, clears pending intent, and removes the matching inverse record. `Session.cancelRouteAction` removes the matching provisional edge and clears intent only after the physical API explicitly fails; if cancellation cannot be saved, pending intent remains durable. Failed writes restore the prior in-memory snapshot; on disk, pending intent continues to force `POSITION_UNCERTAIN`. `Session.unwindRouteStack` applies checked inverse callbacks in LIFO order and persists the shortened stack after every physical inverse before beginning another. Stair traversal now uses the atomic begin/commit/cancel APIs for each move and turn, but mid-slice recovery remains rejected because logical sub-action phases are not persisted.

Snapshots may carry an optional vein excursion `{ stage, checkpoint, visited, frontier, route, blocks }`. `stage` is `entering`, `active`, or `unwinding`; validation bounds the record to V1 excursion limits and checks coordinate keys, frame cursors, inverse actions, and visited-count consistency. An entering record also stores the one-block expected `entryPose` and validates both before and after the seed move. `Session.setVein` saves the pre-entry record with rollback on write failure, and `Session.vein` returns a defensive copy. `Session.commitVeinAction(pose, route, config, vein)` commits a successful physical edge's pose and matching DFS record in one snapshot, clearing the pending action only as part of that save. Active seed entry, traversal edges, inverse edges, and final exact-checkpoint return keep their movement intent pending until this atomic commit succeeds. `Recovery.classify` admits bounded active/unwinding routes only when the persisted cursor, visited coordinates, inverse breadcrumbs, and known route prove a complete unwind to the exact checkpoint. The resume executor then performs only the saved inverse walk; it never resumes ore discovery after reboot. Entering and pending-action states stay refused; longer or malformed unwind shapes fail closed. This covers the MVP traversal-state snapshot requirement while deliberately refusing to restart ore discovery across a reboot.

This satisfies persistence checklist item P01: serializer output is written and closed at `.tmp`, decoded and schema-validated from disk, then installed after rotating the validated active file to `.bak`. `State.load` recovers a validated temp left by interruption before promotion; pending turtle actions still require an uncertainty stop.

Only minimal recovery data is stored: run ID/status, committed pose, known-route graph, small baseline progress descriptor, pending action, reversible route stack, optional landing and vein records, and job-affecting configuration snapshot. Scratch caches, logs, and statistics are excluded.

## Public entry points

Startup saves a `surface_entry / enter_surface` cursor before the first supply check. A reboot while waiting for fuel or torches can therefore be classified and resumed at the known origin. Recovery classifies a supply-short service snapshot by checking its exact mining target as an active cursor; it does not let the temporary supply error bypass route or pose validation. In-slice stair cursors remain unsupported, with a distinct refusal when a saved inverse stack is present.

- `require("src.mining.cursor")` provides `initial`, `mainShaft`, `junction`, `branch`, `stairs`, `withWorkUnit`, and `validate`.
- `require("src.persistence.physical_action").run(session, kind, direction, pose, route, config, invoke)` persists intent before one move, turn, or dig callback and commits/cancels only on a literal callback result.
- `State.new(configSnapshot, pose, route, runId)`
- `State.validate(state)`
- `State.save(state, path, fsApi, textutilsApi)`
- `State.load(path, expectedConfig, fsApi, textutilsApi)`
- `Checkpoint.create(configSnapshot, pose, route, runId, path, fsApi, textutilsApi)`
- `Checkpoint.load(path, expectedConfig, fsApi, textutilsApi)`
- Session methods: `save`, `setProgress`, `resumeCheckpoint`, `service`, `setService`, `vein`, `setVein`, `commitVeinAction`, `recordFloorLanding`, `floorLanding`, `floorLandings`, `routeStack`, `recordRouteAction`, `beginRouteAction`, `commitRouteAction`, `commitRouteInverse`, `unwindRouteStack`, `beginAction`, `commitAction`, `cancelAction`, `markFatal`, `markComplete`, and `status`.

## Invariants and assumptions

- Only literal successful turtle moves/turns advance the durable pose.
- Any persisted pending action is ambiguous after reboot; callers must stop with `POSITION_UNCERTAIN` before movement.
- State files are local to the turtle and use CC:Tweaked `fs` and `textutils` APIs.
- The saved configuration fields must match before loading a run.
- A route snapshot contains the home and current pose as graph nodes; every recorded edge is between adjacent coordinate keys and has a reverse edge.
- The live state machine owns pose/route updates; checkpoint methods copy those values into the durable snapshot at each write.
- `progress.nextAction` names work that has not yet begun; a cursor is persisted before its bounded unit invokes service, digging, movement, or turning.

## Dependencies and limitations

The module depends on injected CC:Tweaked-compatible filesystem and text serialization APIs. `src/mining/main_shaft_resume.lua` exposes `Resume.start(cursor, branchCount, spacing)` to validate and map a saved main-shaft cursor to its first loop branch/cell; `src/mining/junction_resume.lua` maps a supported junction action to the next floor-loop pair; `src/mining/branch_resume.lua` validates/maps lower-outbound and branch return-phase cursors to their exact pair, side, distance, and action. The floor-complete boundary, initial surface entry, next-floor landing crossing, committed main-shaft cell cursor, both junction actions, branch outbound/turnaround/upper-return/junction-descent cursors, validated service stages, and active/unwinding vein inverse routes dispatch through the coordinator. Main-shaft replay resumes at the saved cell and proceeds through remaining shaft pairs. Junction replay resumes before the exact saved action or skips the completed pair. Branch replay continues from the saved phase and position through the remaining return route. Service replay returns to base, repeats unload/resupply, and restores the exact saved cursor pose after route and fuel validation. Vein recovery unwinds only recorded breadcrumbs and clears only at the verified checkpoint. A stair crossing requires complete preceding route landmarks and a recorded path home. Lower-lane return cursors are not emitted; ambiguous seed-entry, in-slice, and landing-carve recovery remain unsupported and fail closed. The recovery classifier is deliberately fail-closed for unsupported executors. Snapshots from an earlier development version that contain only the old generic `active_baseline / continue` marker fail validation rather than being treated as resumable. Unexpected Lua exceptions escaping the coordinator are not intercepted. Crash-injection and manual in-world power-loss testing have not been performed.

## Crash and failure verification

The software crash matrix reloads serialized checkpoints after coordinator cursor writes, service stages, phase transitions, service-route edges, and intermediate vein inverses. Recovery must either admit the exact saved cursor/pose or return an explicit safe stop. Physical-action tests cover intent write failure, literal API failure, exceptions after intent, and commit write failure; persistence tests cover corrupt snapshots, backup recovery, and uncertain pending actions. Run `lua tests/persistence_recovery.lua`, `lua tests/persistence_physical_action.lua`, and `lua tests/persistence_state.lua` from the repository root. This does not simulate actual power loss or establish CC:Tweaked filesystem durability. Controlled-world release procedure and remaining physical gates are in `docs/STATUS.md`.
